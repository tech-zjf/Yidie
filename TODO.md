# Yidie delivery board

This is the single working checklist for the first public, installable release. A box is checked only when its acceptance evidence is recorded. Simulator behavior and physical-device behavior are reported separately.

## Completed

- [x] iOS-first Expo/React Native app with local PhotoKit import, confirmed dates, persistent processing queue, SQLite records, and on-device VisionKit/Vision sticker extraction.
- [x] Calendar-first interaction: sticker stacks, count badges, month-arrow navigation, month/day swipe handlers, animated sheets, centered Add action, English UI, and local identity. Touch-driven paging remains unaccepted until it works on a Simulator touch surface.
- [x] Local sticker style editing: preserve the transparent cutout; preview and save Original, Outline, Comic, 3D, and Shimmer treatments without rerunning segmentation. Prefer VisionKit's public subject-lifting API, crop to visible alpha bounds, and fall back to Vision. Border and shadow geometry scales to the cropped subject and shares one padded canvas across styles; proportional padding keeps the visible subject nearly the same size across source resolutions. Geometry, alpha cropping, compositing, and Core Image pixel checks are separate native modules/tests. The styles use public APIs and are not claimed as 1:1 Photos-app effects.
- [x] Store edited transparent cutouts as revisioned assets. Preview cancellation and failed saves remove only the staged cutout, successful saves atomically point SQLite at the new path before pruning old assets, and backups accept only the matching UUID-derived cutout paths. Isolated native tests cover staging, entry ownership, traversal and symlink rejection, cleanup, version retention, and invalid cross-record references; UI and real-photo behavior remain open below.
- [x] Verify current-tree native renderer pixels with deterministic synthetic transparent pixels on a hosted iPhone Simulator: source color, visible white outline, translucent shadow, stable canvas across resolutions/effects, zero-width identity, and distinct Comic/3D/Shimmer raster output. The current-source GitHub Actions [run 38830000548](https://github.com/tech-zjf/Yidie/actions/runs/38830000548) passed the fixture end to end on commit `0a762aa`. This validates compositing only, not realistic segmentation or visual similarity to Photos.
- [x] Distinguish not-yet-requested, authorized, limited, denied, and restricted Photos access; load an already-authorized library automatically and direct denied users to Settings.
- [x] Fence Settings export/restore/share actions synchronously against rapid duplicate taps; keep the sheet open while an operation or its queue cleanup is active.
- [x] Automated domain/SQLite, TypeScript, lint, formatting, native file-catalog, and documentation-contract checks.
- [x] Route every app launch shortcut through the Simulator-only Expo launcher. It validates an exact available iOS Simulator UDID, supports Debug/Release, and stops before Expo when CoreSimulator is unavailable; tests confirm phone identifiers and missing selections fail closed without launching a device.

## P0 — keep user data safe

- [x] Implement a user-controlled `.yidie` package with a consistent SQLite snapshot and app-owned image assets; the Files picker lets users choose its destination.
- [x] Validate package layout, format/schema versions, checksums, file paths, counts, SQLite integrity, and size limits before restore.
- [x] Stage restores separately and use a startup-recoverable directory swap; rollback retains the current library if activation fails before commit.
- [x] Make backup/restore discoverable in Settings and explain that backup packages are unencrypted and uninstalling without a backup can remove local records.
- [x] Add deterministic native tests for package corruption, malformed foreign-key schemas/data, path traversal, future versions, storage limits, cancellation, interrupted swaps, and a live WAL database; verify a Simulator database can be packaged and staged for restore. On an isolated Simulator, save an empty `.yidie` package through Files, select it in Restore, confirm the 0-record replacement, and relaunch successfully to the calendar.
- [x] Give each repository one owned SQLite connection for reads and `BEGIN IMMEDIATE` write transactions. Serialize every repository operation and shutdown on one FIFO lane; close fences new work and drains the lane. Integration tests use the same transaction adapter and verify read/write/close ordering and rollback.
- [x] If a backup/restore pause request fails, restart only the processing work that was active before the request; preserve manually paused jobs and surface the failure. A regression test injects a failed pause and verifies the prior queue finishes its pending work.
- [x] Smoke-test the SQLite lifecycle fix on an isolated Simulator: restore a valid empty backup while the calendar is running, allow the database replacement/reopen, and confirm the app returns to the calendar. The deterministic regression holds a read, proves a later write cannot enter native SQLite concurrently, then verifies `close()` drains the queue and rejects later work. The Simulator flow did not force a deliberately blocked query at the exact close boundary, so it is lifecycle smoke coverage, not a concurrency stress test.
- [ ] Rebuild the single-connection SQLite change and stress a deliberately held read against a queued write and close/WAL checkpoint on a supported Simulator; verify the app stays open and library data remains available after close/reopen. An earlier crash report showed a statement reset overlapping database close on Expo SQLite's concurrent native queue. The app now routes reads, writes, and close through one owner lane. A new real-file Node SQLite regression holds an actual read transaction, queues a date update and shutdown, then reopens the database, checks integrity, and truncates WAL successfully; Expo SQLite's native-queue and app-lifecycle stress rerun remains required.

## Definition of done

The first public release is done when P0 and P1 code items pass automated checks, all core screens pass a repeatable simulator walkthrough, one opt-in physical-device photo test passes or produces a clearly bounded fallback, all user data flows have rollback behavior, docs agree with the shipped app, CI is green, and a versioned build can be reproduced from the repository. Until then, call it a development build and keep this board current.
