## Verified in this worktree

- On 2026-10-15, ExpoSQLite's Swift importer was found resolving the platform SQLite header instead of Expo's vendored header unless the pod source directory was explicitly included. A tracked Expo config plugin now adds that directory to the ExpoSQLite pod target and has idempotency/template-contract tests. Expo prebuild generated valid Podfile Ruby. A temporary global search-path override built the full unsigned Release app successfully; the no-override build failed. Subsequent clean CocoaPods attempts, including reuse of the local Hermes archive and `--no-repo-update`, stopped because DNS could not resolve GitHub or `cdn.cocoapods.org`; the ordinary clean CocoaPods build remains unaccepted.
- Current checks after the SQLite single-lane change, backup-manifest classification, month-swipe responder change, and Simulator-only launcher: TypeScript, ESLint, Prettier, all 69 domain/SQLite/preview/tool tests, native backup/file-inventory tests (including live-WAL packaging, the picker URL shape, malformed counts, malformed foreign-key schema/data, and oversized declarations), Swift core typecheck, repository/SQL contracts, and packet checks pass. The iOS JS export bundles 700 modules successfully. A malformed foreign-key package is rejected and leaves the current library intact; the initially suspected query-error misclassification was not reproduced because SQLite rejects this schema during statement preparation. Validation now also checks that row scans complete with `SQLITE_DONE`. The repository regression proves overlapping public operations are serialized and close drains the lane; a post-fix unsigned Release build plus empty-backup Simulator restore/relaunch smoke test was completed before this latest serialization change. A queue regression also confirms that a failed backup suspension resumes previously requested work without resuming manually paused jobs. The Simulator launcher tests prove that it forwards only a validated Simulator UDID, rejects physical UDIDs and device names, and stops without invoking Expo when inventory is unavailable; no device was launched in this verification. The latest single-lane change still needs native build and Simulator stress verification. Clean and scene-switching preview bundles both export; the normal Release JavaScript export was checked for and contains no preview scene or fixture code. The standalone Swift exporter typecheck checks API/type correctness, not the rendered image.
- The latest native backup-validation diff passed a complete unsigned iOS Simulator Release app build with Xcode 27.0 across the app and CocoaPods targets. The build did not launch Simulator or access a physical iPhone.
- The month swipe responder now explicitly refuses mid-gesture termination after it has classified a horizontal drag, while vertical movement remains delegated to the calendar scroll view. The pure gesture thresholds are unit-tested; this code change has not yet been verified on a touch surface.
- iOS JavaScript export and unsigned iOS Simulator Release and Debug builds passed in Xcode 27.0. The latest preview source ran on a dedicated iPhone 18 Pro / iOS 27 Simulator. Taps opened a populated month, a same-day ten-entry stack, the day sheet, and the style editor; a dark outline preview was saved and visible on return. This uses synthetic stand-ins and does not verify real Vision cutout quality. Device Hub drag gestures did not change the page or month. The current unsigned Release build was separately installed and launched on the dedicated simulator; the one-screen empty calendar, month arrows, All Records sheet, and Add explainer were checked. The system photo picker was not opened.
- On 2026-10-15, all automated checks passed again. Xcode Components showed iOS 27.0 and 26.1 simulator runtimes already installed; no additional component download was needed. `xcodebuild -list` and a clean unsigned Release build succeeded for iPhone 18 Pro / iOS 27.0. The clean hosted CI job remains necessary to verify a fresh build against pinned Xcode 26.6.
- The latest iOS 26.1 Device Hub pass accepted empty-sheet contents and close-to-calendar state transitions but did not accept swipe gestures or claim frame-accurate exit motion. The first standalone `Simulator.app` launch attempt found no app bundle in the selected Xcode Developer Applications directory; do not infer the Device Hub drag is equivalent to a real touch gesture.
- The current unsigned Release build was installed without erasing the dedicated simulator. Files UI created an 82 KB empty `.yidie` package, and Restore selected it, showed the 0-record/0-image replacement confirmation, completed the restore, closed the app, and relaunched to the October 2026 calendar. The first restore attempt had exposed `URL.hasDirectoryPath` being false for a directory-package URL returned by the document picker; the native bridge now lets filesystem package validation determine the item type, with a regression fixture for this URL shape. Real iPhone and Apple Photos were not accessed.
- No physical iPhone, Photos library, Developer Mode, signing identity, certificate, or keychain was accessed or changed. Xcode regenerated the ignored local iOS project; the Simulator build had code signing disabled.
- The provided crash report is for the Yidie Simulator process. Thread 4 crashed in `exsqlite3_reset`/`SQLiteModule.run` while Thread 5 was in `SQLiteModule.closeDatabase` performing a WAL checkpoint. The repository now serializes all public SQLite operations across its read and write connections, and prevents new calls once close begins. A controlled JS regression passes; the latest change has not yet had a native build or Simulator stress test. The report alone does not identify the screen/action that initiated close.
