# 市场调研与差异化

衣叠可以做，但需要以小规模验证控制投入。穿搭日历、自动抠图、批量导入、本地保存和月历海报都已有产品覆盖；值得投入的是一套清晰、顺手、可展示的交互，以及完整可复现的开源实现。单纯换成白底日历，难以形成持续吸引力。

研究截至 2026-10-13。以下功能来自产品官网、应用商店说明和公开仓库，属于公开声明；未对这些 App 做付费安装后的完整操作对比，未公开提到不等于没有该功能。

## 已有产品

| 产品 | 已公开的相关功能 | 与衣叠的关系 |

## 具体做什么差异

| 方向 | 衣叠的可交付行为 | 为什么值得试 | 差异证据强度 |
| --- | --- | --- | --- |
| 同日多套穿搭 | 一天允许多张；月历最多露出 3 层；轻微错位；点击后横向展开；可改封面 | 一天出门、通勤、聚会不用被迫只留一套，演示视频容易看懂 | 体验主张，尚未证明竞品都缺失 |
| 满月也清楚 | 有记录用贴纸替代数字，空格显示日期；四、五、六周自适应；叠放层数受控 | 解决“演示几张好看，记录多了就糊”的实际问题 | 可用性质量，需用户照片验证 |
| 日期可纠正且可解释 | 批量导入预览分组；日期来源可见；缺失日期待归档；指定日导入优先于照片时间 | 老照片、截图、聊天保存图能可靠整理 | 基础体验做深，非新发明 |
| 屏幕与分享一致 | 所见月历直接导出；同一贴纸位置、封面、角度；署名可关 | 用户自己的穿搭能产出值得分享的图片 | 现有海报功能上的完成度，非功能独占 |
| 完整的开源本地链路 | 无业务账号、无 API Key、无需部署；Swift 抠图模块、日期规则、测试、构建说明都公开 | 给开发者提供可运行、能学习、能复用的具体价值 | 相比服务部署型开源方案更明确，但不是绝对唯一 |

定位建议：**“把每天的多套穿搭，叠成自己的月历。”** README 次级介绍强调：**“An offline iOS outfit sticker calendar built with Expo and Apple Vision.”** 两句话分别服务普通用户和开发者。

不能拿来宣传成独有能力：系统本地抠图、照片 EXIF、开源、无账号、旋转贴纸、中文、导出月历。也不要描述为“市场上唯一”“尚无竞品”。

## 可玩性如何取舍

首版只打磨“叠起来—展开—换封面—分享”这个动作。贴纸出现时轻微落下和回弹，展开时保持视觉位置关系，减少动效设置时立即切换。封面顺序和角度保存下来，下次打开不会重新洗牌。

后续可验证两个方向：月末按日期逐张落下的短动画导出；把一段旅行或一周穿搭导出成自由贴纸页。这些需要首版有人使用后再做。天气推荐、AI 试衣、社区、衣橱商品库、每日打卡排行会明显扩大成本，暂不进入路线图。

## 用户、Star 与安装门槛

普通穿搭用户关注好不好装、抠图是否漂亮、能不能快速回看；开源开发者关注实现质量、复现难度、是否有技术内容可以学习。两者不能用一个 Star 数混为一谈。

初期不进入 App Store，真实使用的最大阻力可能是安装。iOS 没有面向所有人的通用“下载 IPA 即安装”方式。自行签名和 Xcode 适合开发者；Apple Personal Team 的描述文件有效期有限，官方说明为 7 天。TestFlight 适合后续测试分发，但需要开发者计划与 App Store Connect 流程，外部测试可能需要审核。它不等于公开上架，也不等于无成本、永久免维护。[Apple 账号说明](https://developer.apple.com/help/account/basics/about-your-developer-account)、[TestFlight](https://developer.apple.com/testflight/)

因此先以“愿意本地构建的 iOS / RN 开发者 + 少量愿意反馈的穿搭用户”为受众。公开的浏览器交互演示可降低看懂项目的门槛，但不替代安装或真实使用数据。

## 投入与停止条件

建议先投入 3–5 个有效开发日完成原生验证与单条链路，随后才决定完整首版。完整范围按熟悉 RN、需要适配 Swift 的单人估计约 15–25 个有效开发日，属于规划估算，不是交付承诺。

以下是为本项目自定的判断门槛，不是行业基准或增长预测：

1. 用 20 张有代表性的照片做离线抠图，其中至少 16 张不经精修即可接受；否则先调整输入或产品预期。
2. 找到 5 位目标体验者，其中至少 3 位可以独立导入 10 张照片、理解同日叠放并导出月历。
3. 一周后至少 2 位主动继续记录或愿意分享自己的月历；重点听他们为什么继续或为什么放弃。
4. 开源展示后观察 2–4 周：是否出现真实构建成功反馈、外部 issue、贡献意愿；Star 只做辅助信号。

如果安装阻力让所有体验都停在第一步，先解决测试分发，再判断需求强弱。若能顺利体验仍无人愿意继续用，则将项目收束为一个完成度高的技术作品，避免持续增加功能追逐关注。
